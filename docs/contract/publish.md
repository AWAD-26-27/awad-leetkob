## 1. Conventions

- **Protocol & Encoding:** All HTTP requests and responses use JSON encoded in UTF-8.
- **Identifiers:** `labId` is a positive integer representing the unique ID of a lab.
- **Timestamps:** All timestamps are formatted date-time strings in UTC (`YYYY-MM-DD HH:mm:ss`), matching the system clock with 1-second resolution.
- **Authentication:** Callers authenticate via the `Authorization: Bearer <token>` HTTP header. (In demo/testing environments, demo tokens such as `tok-ta-b` or `tok-admin` are accepted).
- **Forward Compatibility:** 
  - Clients must ignore unknown response fields.
  - The server ignores any request body submitted to endpoints that do not specify a request body.

## 2. Error Model (RFC 9457 Problem Details)

Every 4xx and 5xx response returned by this API is a **Problem Details** object conforming to RFC 9457, served with `Content-Type: application/problem+json`:

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://leetkob.example/problems/reviews-pending",
  "title": "Reviews pending",
  "status": 409,
  "pending": 1
}
```

### 2.1 Problem Details Members

| Member | Type | Required | Description & Constraints |
|---|---|---|---|
| `type` | URI String | Yes | Absolute URI identifying the problem type: `https://leetkob.example/problems/<slug>`. Clients must branch on `type`, never parsing titles. |
| `title` | String | Yes | Human-readable summary of the problem type. |
| `status` | Integer | Yes | The HTTP status code generated by the origin server for this occurrence. |
| `pending` | Integer | Conditional | **Only present on `409 reviews-pending`**. Positive integer representing the exact count of submissions remaining in the TA review queue. |

### 2.2 Error Slugs & HTTP Status Codes

| Slug | Status | Title | Trigger Condition | State Invariant |
|---|---|---|---|---|
| `unauthenticated` | 401 | `Sign in first` | Missing `Authorization` header, or token not found in the users store. | Database unchanged (`published_at` remains unaffected). |
| `forbidden` | 403 | `Only staff of this class may publish` | Caller is an enrolled student of the class owning this lab. | Database unchanged (`published_at` remains unaffected). |
| `not-found` | 404 | `No such lab` | Lab ID does not exist in the database, ID is invalid, OR caller is a TA/user from outside this class. | Database unchanged (`published_at` remains unaffected). Same body prevents resource enumeration. |
| `reviews-pending` | 409 | `Reviews pending` | One or more submissions for this lab have a verdict requiring human review (`violation` or `unsure`) without a recorded TA decision (`decision IS NULL`). Response includes `pending`. | Database unchanged (`published_at` remains `NULL`). |
| `internal` | 500 | `Something went wrong` | Unhandled server or database exception during request execution. | Request terminates; uncommitted mutations are aborted. |

## 4. Endpoint Specification: `POST /api/labs/{labId}/publish`

Publishes the final marks and verdicts of an Accepted lab submission set to students. This action is the **Human Gate** of LeeTKOB: it must only succeed once the TA has audited all flagged submissions.

### 4.1 Request

- **HTTP Method & Path:** `POST /api/labs/{labId}/publish`
- **Path Parameter:**
  - `labId` (required, positive integer): Unique identifier of the lab.
- **Request Headers:**
  - `Authorization: Bearer <token>` (required)
- **Request Body:** None expected. If a client submits a body, the server ignores it.

### 4.2 Caller & Ownership Matrix

| Caller Role & Context | HTTP Result | Behavior & Security Rationale |
|---|---|---|
| No token / Unknown token | `401 unauthenticated` | Authentication required. |
| Student enrolled in the lab's class | `403 forbidden` | Students know the lab exists but are forbidden from publishing grades. |
| TA or user from another class | `404 not-found` | Returned identical to non-existent labs to prevent class/lab existence probing. |
| Non-existent or non-numeric `labId` | `404 not-found` | Resource does not exist. |
| TA assigned to the lab's class, or Admin | `allowed` | Subject to the evaluation order below. |

### 4.3 Evaluation Order (Server Decision Tree)

The server evaluates the request in the following strict order, terminating at the first failure:

```
[Request Received]
       │
       ▼
1. Extract Bearer Token ──────────────> [Missing / Unknown] ──> 401 unauthenticated
       │
       ▼
2. Lookup Lab by labId ───────────────> [Not Found / NaN]  ───> 404 not-found
       │
       ▼
3. Check Staff Authorization:
   - Admin or Class TA? ──────────────> [Enrolled Student] ───> 403 forbidden
                                        [Outsider / Foreign TA] > 404 not-found
       │ (Authorized)
       ▼
4. Check Idempotency:
   - lab.published_at IS NOT NULL? ───> [Already Published] ──> 200 OK (Return existing publishedAt,
       │ (Not published yet)                                          skip pending reviews check)
       ▼
5. Check Review Pending Queue:
   - Count submissions where
     verdict IN ('violation','unsure')
     AND decision IS NULL > 0 ────────> [Pending Count > 0] ──> 409 reviews-pending (pending: N)
       │ (Pending Count == 0)
       ▼
6. Publish Lab:
   - Atomically execute:
     UPDATE labs SET published_at = datetime('now') WHERE id = labId AND published_at IS NULL;
   - Return 200 OK with { lab, publishedAt }.
```

### 4.4 Idempotency & Repeat Safety

- **Safe to Repeat:** Network timeouts, dropped connections, or accidental double clicks may cause clients to retry `POST /api/labs/{labId}/publish`.
- **First Call (when pending count = 0):** Sets `published_at = datetime('now')` and returns `200 OK`.
- **Subsequent Replays:** Because `published_at` is already non-null, the server returns `200 OK` with the **identical, originally recorded `publishedAt`**. It does not re-verify pending submissions, does not alter marks, and does not move the clock forward.
- **Concurrent Requests:** The SQL mutation `WHERE id = ? AND published_at IS NULL` ensures race conditions cannot create multiple publication timestamps.

## 5. Versions and Evolution Policy

- **Current Version Baseline:**
  - The endpoint `POST /api/labs/{labId}/publish` operates within the unversioned `/api/` path, serving as the canonical v1 baseline for the grade publishing service.
- **Additive Changes (Backward-Compatible):**
  - Introducing new optional response fields (e.g., `totalPublishedCount`).
  - Introducing new problem types (`type` slugs) for newly recognized error conditions.
  - These changes are permissible directly within the current `/api/` namespace without breaking existing clients.
- **Breaking Changes:**
  - Altering the existing URL path, removing or renaming existing fields (`lab`, `publishedAt`).
  - Modifying the HTTP status codes or semantics of existing errors (401, 403, 404, 409).
  - Changing timestamp formats or making previously optional fields mandatory.
  - Breaking changes require introducing a new major version path prefix (e.g., `/api/v2/labs/{labId}/publish`), with the existing `/api/` endpoint maintained under a declared deprecation schedule before sunsetting.
- **Coordinated Updates:**
  - Any contract amendment must be committed together with corresponding contract tests (`test/contract/`) and backend updates (`src/app.js`) in an atomic pull request.
